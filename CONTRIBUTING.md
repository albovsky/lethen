# Contributing to lethen

Lethen continues the MIT-licensed Periphery codebase. Contributions are accepted under the repository's MIT license; retain existing copyright and license notices.

Start with `swift build --product lethen` and `swift test`. Xcode integration tests need full Xcode and the fixture SDKs. Include your OS, Swift and Xcode versions in bug reports, together with the command, relevant configuration, and a minimal reproducible project. Remove secrets and proprietary code before sharing fixtures.

Analysis changes should include a regression test demonstrating both declarations that must be reported and declarations that must be retained where applicable. Discuss major features and dependency or distribution changes in an issue first. Prefer small, reviewable patches; generated or AI-assisted changes need the same evidence as any other contribution.

Initial scope is compatibility and correctness maintenance. Support is best-effort. Existing Periphery configuration and comment syntax remain compatible. Do not mass-rename internal modules or fixtures as part of branding changes.

CI runs in profiles chosen by `.github/scripts/plan-ci.sh`: pull requests build the newest stable toolchain per platform (Swift 6.4/Xcode 27, macOS 6.3, Linux 6.3, Bazel 9.x; Linux 6.4 waits on #27) because hosted macOS runs only five jobs at once; pushes to `master` add Bazel 8.x, and the nightly schedule adds the main-snapshot toolchains. Lethen supports the current Xcode major and the final release of the previous major, the Swift toolchains they ship, the same Swift minors on Linux through the official containers, and the current and previous Bazel LTS; the matrix follows that policy. Run the `Test` workflow manually with the `nightly` profile to exercise the full matrix on a branch. Documentation-only changes skip the build jobs. The nightly run also prunes Actions caches left behind by merged or closed pull requests and deleted branches (`.github/scripts/prune-caches.sh`, which takes `--dry-run` locally), so live caches are not evicted to make room for dead ones. The `Required checks` job is the single gate for branch protection; it fails unless every job its profile expects has succeeded.

Run `bash .github/scripts/verify-swift-6.4.sh` for the required Xcode 27 baseline. It verifies the toolchain, runs the full suite, compares clean/warm/native fixture findings, and performs a strict self-scan. Evidence is written to `.validation/`. The matching GitHub check is required on `master`; test setup errors must fail tests, and new analysis behavior needs both reported and retained controls. Use `swift build --show-bin-path` to locate executables rather than assuming a build-engine layout.

Pushing a version tag releases it through the `Release` workflow (`.github/workflows/release.yml`). Set `PeripheryVersion` and add `docs/releases/<version>.md` in a pull request, merge it, then tag the merge commit on `master`. The workflow refuses a tag that does not match `PeripheryVersion`, is not on `master`, or whose commit did not pass `Required checks`; it waits for a gate that is still running. It builds the Apple silicon macOS binary with the oldest supported Xcode and the same `swift build -c release` as a source installation, smoke-tests it (version, then a scan that must report exactly one known unused function), and waits for approval in the `release` environment. The approved job signs it with the Developer ID certificate and hardened runtime, notarizes it, smoke-tests the signed binary, and publishes the release with `lethen-<version>-macos-arm64.zip` and `SHA256SUMS`. There is no Intel binary: Xcode 27's libIndexStore has no x86_64 slice, so Intel Macs build from source while Xcode 26 remains supported. Stable versions then update `Formula/lethen.rb` in `albovsky/homebrew-tap` after `brew install` and `brew test` pass against the new formula; prereleases (`3.9.0-dev.1`) are published as GitHub prereleases only, and the update checker offers them only to development builds. Run the workflow manually with an existing tag to backfill binaries or retry a failed release. A published zip is never replaced, because the formula pins its checksum: reruns reuse it, and the tap never moves to an older or equal version. The macOS binary finds libIndexStore in `/Applications/Xcode.app`, `/Applications/Xcode-beta.app`, or the Command Line Tools (`.github/scripts/release-relocate-rpaths.sh`). Linux tarballs for x86_64 and aarch64 come from `.github/workflows/release-linux.yml`, which `Release` calls for a tag and `Test` calls for every code change as part of `Required checks`: it builds with Swift 6.3 on Ubuntu 22.04 and `--static-swift-stdlib`, packages `bin/lethen` (a launcher that puts the active `swiftc` toolchain's lib directory on `LD_LIBRARY_PATH`) with `libexec/lethen/lethen`, and smoke-tests them with the Swift 6.3 and 6.4 images and a swiftly toolchain. The executable links libIndexStore symbols versioned `LLVM_21`, so it cannot run with Swift 6.1 or 6.2, and a Swift that moves to a newer LLVM needs a new Lethen release. Every asset already published is reused on reruns, so adding Linux tarballs to a release that already has `SHA256SUMS` fails instead of rewriting it.

The signing, notarization, and Homebrew credentials live only in the `release` environment. Do not use upstream credentials or publish into upstream registries. Tags through 3.8.0 are upstream history, not lethen releases.
