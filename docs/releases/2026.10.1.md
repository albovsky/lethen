# lethen 2026.10.1

Lethen 2026.10.1 is the first release with a calendar version (`YYYY.M.N`; see [CONTRIBUTING](https://github.com/albovsky/lethen/blob/master/CONTRIBUTING.md#validation-and-releases)). It scans an Xcode project in several build configurations at once, so code compiled out of one configuration is no longer reported as dead; it grades results more accurately and reports uncertain ones one severity lower in CI; and it reuses completed Xcode builds. It requires Swift 6.3 (Xcode 26.4) or later, like 3.10.0.

## Breaking changes

- `--configurations` on an Xcode project builds only one listed configuration for testing, the scheme's Test configuration or, when that is not listed, the first one listed. Every other listed configuration builds the scheme's Run action. Test targets are compiled and indexed once, in the configuration that builds them, so a project that relied on its test targets compiling in each listed configuration no longer gets their references from the others. A configuration in which the tests do not compile, or that has no testability, can now be listed. A scan without `--configurations` is unchanged.
- `likely` results are reported one severity lower than `certain` ones in the CI formats: a `::notice` annotation in `github-actions`, `severity="info"` in `checkstyle`, and `"severity": "minor"` in `codeclimate`. A pipeline that failed or gated on those severities sees fewer warnings and errors. `--strict` still counts both.
- Library clients of `PeripheryKit` and its `Indexer` module: `IndexPipeline.perform()` returns an `IndexResult` that carries the confidence evidence, and `ScanResultBuilder.build(for:configuration:confidence:)` takes a `ConfidenceAssessor`. The command line and its output are unchanged.
- The first SwiftPM scan after upgrading cleans once, because the build stamp format changed.
- Tags and the GitHub Action's `version` input reject zero-padded versions such as `2026.09.1`, which are not valid Semantic Versioning. `2026.10.1` ranks above every 3.x release.
- The Bazel module override in `MODULE.bazel` must still be the same version as the binary: set its `tag` to `2026.10.1`.

## Highlights

- **Several build configurations.** `lethen scan --configurations Test Debug` on an Xcode project reads the index of each configuration, so a declaration reachable only in one, such as the real launch path in the `#else` of `#if TEST`, is no longer dead. The result is the same on every run, which two bugs (#158 and #165) had broken before this release. Lethen also picks the only shared scheme when `--schemes` is missing, and says so.
- **Better confidence.** Every result is `certain` or `likely` with a reason, and the reasons are narrower: a name in a bare string literal no longer makes a pure-Swift declaration `likely`, a name in a skipped `#if` branch must fit the labels and the type the branch spells, an Objective-C-accessible declaration is `certain` once Lethen has read every Objective-C unit of the build, and a declaration used only by an Xcode target the scanned schemes do not build is `likely` with a warning that names the target.
- **Objective-C.** Unused `@import` lines in `.m` files are reported again from clang's index, and string literals and `@selector(...)` names in Objective-C files count for the string-literal rule.
- **Fewer false positives.** Fixed classes include synthesized `Codable` reads, decoded models returned through a generic client, witnesses of public protocol requirements, App Intents requirements, copies of a declaration from the other branch of an `#if`, initializers in extensions of types the scan does not declare, string-literal selectors, and file-system-synchronized folders shared between targets.
- **Faster rescans.** An Xcode scan runs no `xcodebuild` when nothing a scan reads has changed since Lethen's last completed build. A rescan of Wikipedia iOS with nothing changed takes 7.1 s instead of 24.2 s, and 7.6 s with two configurations. A SwiftPM package with a target the build never compiles, such as a plugin-only executable, now reuses its build: swift-argument-parser rescans in 4.6 s instead of a 38.2 s clean build (Linux, Swift 6.4).
- **`--verbose` is safe with `--format json`.** Its log goes to standard error.

## Measured results

All figures come from `docs/validation/precision-corpus.md` and `docs/validation/scan-performance.md`, with the toolchains and commits recorded there. They were not re-measured head to head against 3.10.0.

| Release criterion | Target | Result | Met |
| --- | --- | --- | --- |
| Wikipedia iOS `likely` share | under 10 % | 1.6 % (42 of 2,567 findings, `--configurations Test Debug`); 11.2 % (310 of 2,769) in the Test configuration alone, from 15.6 % (432 of 2,769) before the last batch of changes | yes, with both configurations |
| Sampled precision on the corpus | 95 % | 92.2 % (83 TP, 7 FP of 90 sampled findings) | **no** |
| Precision of sampled `certain` findings | not a release criterion | 100.0 % (81 of 81) | n/a |
| Wikipedia no-change rescan skips `xcodebuild` | yes | yes, 7.1 s | yes |
| swift-argument-parser warm scan reuses the build | yes | yes, 4.6 s, 0 modules recompiled | yes |

Sampled precision was 73 % at the first measurement, 84.0 % in 3.10.0 and 90.7 % before the last batch of changes. The 95 % target is not reached: the corpus now holds four projects, including IceCubesApp, a pure-Swift SwiftUI app, and it pulls the figure down (77.8 % over 18 sampled findings, up from 56.0 % before this release's fixes). The seven false positives left are all `likely`: two compiled-out `#if targetEnvironment(macCatalyst)` rows and two `Encodable` rows in IceCubesApp, and three Linux-only declarations that swift-nio uses when scanned on macOS. Sample sizes are small (18 to 29 findings per project), so treat the figures as indications, not guarantees.

Lethen reports `fetchFeatureConfig(completion:)` of Wikipedia iOS as used, because Objective-C code at `MWKDataStore.m:924` sends it, a use Periphery does not see (#141). The Periphery comparison numbers have not been re-run for this release.

## Fixes

The full list is in `CHANGELOG.md`. Among them: two projects of a workspace that define targets of the same name are no longer merged (#112); `--exclude-targets` no longer lets a storyboard that only an excluded target owns retain classes (#135); the warning about excluded targets that depend on scanned targets now appears for real packages.

## Verification and limits

The release commit must pass the `Required checks` gate: the Swift 6.4 / Xcode 27 baseline, the macOS 6.3 / Xcode 26.4 job, Linux 6.3 and 6.4, Bazel on macOS and Linux, and the Linux release tarballs smoke-tested on Ubuntu 22.04, 24.04 and 26.04 images. The [verified combinations](https://github.com/albovsky/lethen/blob/2026.10.1/README.md#verified-combinations) table still lists the 3.10.0 binaries and release run; it has no 2026.10.1 row yet, so nothing in it is evidence for this release. The [precision scorecard](https://github.com/albovsky/lethen/blob/2026.10.1/docs/validation/precision-corpus.md) records how precision is sampled. Intel source builds are not tested in CI.

## Platforms and installation

**Platforms:** macOS release binaries and Homebrew are Apple silicon only (macOS 15 or later). Intel Macs build from source with a supported Xcode 26.x; see the [platform policy](https://github.com/albovsky/lethen/blob/master/CONTRIBUTING.md#supported-platforms). Linux x86_64 and aarch64 can use the release tarballs, which need glibc 2.35 or later and a Swift 6.3 or newer toolchain, or build from source.

Install with `brew install albovsky/tap/lethen`, or download the [arm64 zip](https://github.com/albovsky/lethen/releases/download/2026.10.1/lethen-2026.10.1-macos-arm64.zip) and [checksums](https://github.com/albovsky/lethen/releases/download/2026.10.1/SHA256SUMS). Xcode or the Command Line Tools must be installed. On Linux, download `lethen-2026.10.1-linux-x86_64.tar.gz` or `lethen-2026.10.1-linux-aarch64.tar.gz`. The [installation guide](https://github.com/albovsky/lethen/blob/master/docs/guide.md#installation) includes checksum verification; the [README](https://github.com/albovsky/lethen/blob/2026.10.1/README.md#linux) shows how to install a Linux tarball.

### Source installation

Select a full Xcode installation on macOS, for example `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`, then:

```sh
git clone --branch 2026.10.1 --depth 1 https://github.com/albovsky/lethen.git
cd lethen
swift build -c release --product lethen
lethen_bin_dir="$(swift build -c release --show-bin-path)"
"$lethen_bin_dir/lethen" version
mkdir -p "$HOME/.local/bin"
install -m 755 "$lethen_bin_dir/lethen" "$HOME/.local/bin/lethen"
export PATH="$HOME/.local/bin:$PATH"
lethen scan --project-root /path/to/your/project --disable-update-check
```

Keep the PATH export in your shell profile. Stable builds are offered stable releases by the optional update checker.
